# Skill: TDD, Micro-Task Slicing & Atomic Git Workflow

This skill governs **how** work is planned, tested, implemented, and prepared for version control in **Restaurant Tickets (El Chupacabras)**. Every task executed by the agent must adhere to these constraints.

---

## 1. Zero-Monolith Rule (Micro-Task Slicing)

**NEVER generate massive code dumps (e.g., thousands of lines of code or a "grocery list" of 20+ unrelated files in a single task).**

Every feature or User Story (`HU-001` through `HU-015`) must be decomposed into **vertical, verifiable micro-tasks**:

1. **Slice by Layer or Scenario:**
   - *Slice 1:* Domain aggregate/value objects + unit tests (e.g., `Solicitud` & `Dinero` invariance tests).
   - *Slice 2:* Database migration / JPA entity mapping + repository test (`@DataJpaTest`).
   - *Slice 3:* Single application service method / domain policy + unit tests (e.g., `ValidadorDisponibilidad`).
   - *Slice 4:* REST Controller endpoint + BDD/Gherkin acceptance tests (`@WebMvcTest` or integration test covering 200/201/400/403/409/422).
   - *Slice 5:* Isolated React component / hook + Vitest/Testing Library test.
2. **Size Thresholds per Slice:**
   - Target **≤ 300 lines of code** added/modified per slice.
   - Touch **≤ 6 files** per atomic change set.
   - Each slice must leave the project compiling and all tests green.

---

## 2. Strict Test-Driven Development (TDD: Red -> Green -> Refactor)

No production business logic may be written before its corresponding failing test.

### Step 1: RED (Write the Failing Test First)
- Locate the exact Gherkin scenario in `docs/05-historias-y-criterios/` or business rule in `docs/03-reglas-de-negocio/`.
- Write a focused test asserting the expected behavior, invariant, or HTTP response status (`201`, `400`, `403`, `409`, `422`).
- Run the test suite to confirm the test fails for the expected reason.

### Step 2: GREEN (Write Minimal Production Code)
- Write **only** the production code required to make the failing test pass.
- Do not add speculative abstractions, extra endpoints, or unrequested features.
- Re-run the test to confirm it passes.

### Step 3: REFACTOR (Clean Up While Green)
- Eliminate duplication, improve naming using the **Ubiquitous Language** (`docs/06-modelo-de-dominio/COMP-02-modelo-de-dominio.md`), and verify hexagonal boundaries (Domain has zero dependency on Spring Web or JPA annotations where pure DDD is used).
- Re-run the full relevant test suite to ensure zero regressions.

---

## 3. Git Policy & Authorship Restrictions (NON-NEGOTIABLE)

1. **NO AI Commits:**
   - The agent **MUST NOT** execute `git commit` or `git commit --amend`.
   - All commits are authored and executed exclusively by the human developer.
2. **NO AI Attribution or Trailers:**
   - Never suggest, inject, or configure `Co-authored-by: Gemini`, `Generated by AI`, or any similar trailer in commit templates, PR descriptions, or source comments.
3. **Allowed Non-Destructive Git Assistance:**
   - The agent may run `git status`, `git diff`, `git log -n 10`, `git branch`, and `git add <specific-files>` to help stage a clean, atomic change set for the user to review.
   - The agent may propose a concise Conventional Commit message for the user to run manually:
     ```text
     feat(pedidos): validate stock availability before payment [HU-001] [RF-014] [RN-015]
     ```
4. **Forbidden Destructive Git Commands:**
   - Never run `git reset --hard`, `git clean -fd`, `git push --force`, `git rebase`, or branch deletions without explicit user instruction.
